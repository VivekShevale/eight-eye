## 1. Commands per framework

| Task | Alembic (FastAPI) | Flask-Migrate | Django |
|---|---|---|---|
| Initialise once | `alembic init -t async migrations` (sync: `alembic init migrations`) | `flask --app run.py db init` | (built in) |
| Create migration | `alembic revision --autogenerate -m "add expense audit columns"` | `flask --app run.py db migrate -m "add expense audit columns"` | `python manage.py makemigrations <app>` |
| Apply | `alembic upgrade head` | `flask --app run.py db upgrade` | `python manage.py migrate` |
| Current state | `alembic current` | `flask --app run.py db current` | `python manage.py showmigrations <app>` |
| History | `alembic history` | `flask --app run.py db history` | `showmigrations` |
| Show SQL | `alembic upgrade head --sql` | `flask db upgrade --sql` | `python manage.py sqlmigrate <app> <number>` |
| Undo last | `alembic downgrade -1` | `flask db downgrade` | `python manage.py migrate <app> <previous>` |

## 2. Alembic setup (FastAPI)

In `migrations/env.py`:

- Read the URL from the app config, not from `alembic.ini`: `config.set_main_option("sqlalchemy.url", settings.database_url)`.
- `target_metadata = Base.metadata`, and import `app.models` so every model is registered (`app/models/__init__.py` imports each model and lists them in `__all__`).
- `compare_type=True` in `context.configure(...)` so column type changes are detected.
- Keep `alembic.ini` free of credentials.

## 3. Workflow for every schema change

1. Change the model.
2. Generate the migration with a descriptive message.
3. **Read the generated script.** Autogenerate misses or misreads things: renames appear as drop + add (data loss), server defaults, enum changes, and constraints without names.
4. Check `downgrade()` reverses `upgrade()`.
5. Apply it locally and test the feature.
6. Commit the model change and the migration in the same commit.

## 4. Safe patterns for risky changes

**New NOT NULL column on a table with rows**

```python
def upgrade():
    op.add_column("expenses", sa.Column("expense_time", sa.Time(), nullable=True))
    op.execute("UPDATE expenses SET expense_time = '00:00:00' WHERE expense_time IS NULL")
    op.alter_column("expenses", "expense_time", nullable=False)
```

A constant default can instead use `server_default=sa.text("now()")` on the column.

**Rename a column (keep data)**: replace the autogenerated drop/add with `op.alter_column("expenses", "date", new_column_name="expense_date")`.

**Named constraints**: with the naming convention in `assets/base.py`, autogenerate names every FK, unique and check constraint, so `downgrade()` can drop them. A migration containing `None` as a constraint name will fail on downgrade; fix the name before applying.

**New foreign key on existing rows**: add the column nullable, backfill, then add the constraint.

**Large tables**: create indexes concurrently in PostgreSQL (`postgresql_concurrently=True` inside an autocommit block) when the table is big and in production.

## 5. Fixing drift and broken migrations

- "column does not exist" / "relation does not exist": a migration wasn't applied, or was edited after being applied. Run the current-state command, compare with the real columns (`SELECT column_name FROM information_schema.columns WHERE table_name = 'expenses';`), then apply or add a corrective migration.
- Never edit a migration that was already applied: the database won't run it again, so the edit silently does nothing. Create a new migration that makes the correction.
- A migration failing halfway on PostgreSQL rolls back (transactional DDL); fix the script and rerun. On MySQL, DDL isn't transactional; check what was applied before retrying.
- Squashing or deleting migrations and resetting the database is acceptable only for a disposable local database, only with the user's explicit go-ahead, and the result is committed as one clean migration.
